# 08-仿真训练

[返回首页](../README.md) · 上一章：[功能测试](07-测试站立坐下与走路.md)

**目标：**在训练电脑上建立与真机相符的环境，完成小规模运行检查、正式训练、回放、导出和部署验证。已有经过验证的配套模型时，本章是进阶内容。

本教程真机目标已经确定为 **ZERO 3W + 飞特 HD-1910-C001 + HAT**。公开工程或参数文件名中的“HD1910”不能单独证明其固件控制模式、执行器参数与 C001 一致，训练与部署仍需对照本套 BOM、实际固件和模型合同。

## 1. 训练在哪里运行

| 设备 | 工作 |
| --- | --- |
| Linux + NVIDIA CUDA GPU，或已正确配置 CUDA 的 WSL2 | 并行仿真与强化学习训练 |
| 支持对应仿真依赖的电脑 | 模型检查、CPU 回放、结果分析 |
| Radxa ZERO 3W | 运行已导出的策略、读传感器、控制真机，不承担大规模训练 |

本章示例使用 [microduck-replica 的 HD1910 训练基线](https://github.com/fanhao375/microduck-replica/tree/master/software/training)，便于与 Studio 文档衔接。它的源码说明明确：**基线尚无该工程本机实测通过的走路策略，部分质量惯量仍沿用原版**。跑通示例不会自动得到可交付的步态。

[Ley-WL/microduck-rl](https://github.com/Ley-WL/microduck-rl)是另一条 HD1910/Observer 适配路线，已有特定模型和合同；它不是与 robotd 即插即用的同一部署接口。两套工程的任务、HOME、限位、动作滤波和参数不能交叉拼接。

## 2. 先把硬件模型对齐

训练前记录并核对：

- 机体结构、关节轴、正负方向、零位与关节顺序。
- 每段质量、惯量、重心，实际电池/主控/外壳重量和安装位置。
- 脚底接触几何、摩擦和机械限位。
- HD1910 执行器模型、P/D、电压、限力、摩擦、回差、延迟与通信节拍。
- IMU 安装方向、陀螺仪单位、投影重力的坐标约定。
- 观测顺序、归一化、上一动作的定义、动作幅度与滤波。

借用公开 BAM 参数不等于完成本机执行器辨识。换舵机后不能把 XL330 的默认参数当成 HD1910 参数；质量和电池位置变更也需要重新核验模型，必要时适配或重训。

## 3. 安装固定版本的训练环境

在**训练电脑 Linux/WSL 终端**运行，先按 [uv 官方说明](https://docs.astral.sh/uv/getting-started/installation/)安装工具，确认 `nvidia-smi` 能识别 GPU。

示例固定源码提交，避免同名命令随仓库更新变化：

```bash
git clone https://github.com/fanhao375/microduck-replica.git microduck-training
cd microduck-training
git checkout e20877b8a099e8d669ef14e7f22275a946625f55
cd software/training
uv sync --frozen --python 3.12
uv run --frozen list-envs
```

这里训练环境的 Python 3.12 与 Studio 参考版的 Python 3.13 属于不同设备/环境，不要在瑞莎系统里随意切换解释器来同时满足两者。

## 4. 先跑 64 环境、5 轮的流程检查

```bash
uv run --frozen train Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --env.scene.num-envs 64 \
  --agent.max-iterations 5 \
  --agent.logger tensorboard
```

检查模型可加载、环境能步进、无 NaN/持续报错、日志和 checkpoint 能保存。日志参考位置为 `logs/rsl_rl/microduck_hd1910_velocity/`。

这一步只检查训练链路，**5 轮不会学会走路**，其输出不能直接装到真机。

失败先检查 CUDA、依赖锁文件、显存、任务名和资产路径。不要用 `--no-bam` 或删掉限位来绕过与硬件相关的错误。

## 5. 正式训练与实验记录

流程检查通过后，根据显存逐步增加并行环境和训练轮数。下列规模是命令示例，不保证适合所有 GPU，也不保证到该轮数即可稳定行走：

```bash
uv run --frozen train Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --env.scene.num-envs 1024 \
  --agent.max-iterations 3000 \
  --agent.logger tensorboard
```

每次记录源码提交、任务 ID、依赖锁文件、硬件模型摘要、随机种子、训练参数、奖励修改、checkpoint 和回放结论。先保留未修改的基线，再一次改变一类因素。

仿真要检查保持站姿、起停、前后左右指令、转向、扰动与不同初始状态；观察跌倒率、关节限位、脚底滑移、电机需求和跟踪误差，不能只看奖励曲线升高。

## 6. 从指定 checkpoint 导出 ONNX

在同一训练环境导出，先明确选哪一个 checkpoint，保留训练配置和归一化。设置变量为实际绝对路径，不把下面示例路径原样执行：

```bash
MICRODUCK_CHECKPOINT="/实际训练目录/model_2999.pt"
mkdir -p exports
uv run --frozen python scripts/export.py Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --checkpoint-file "$MICRODUCK_CHECKPOINT" \
  --onnx-file exports/policy.onnx \
  --num-envs 1
```

导出参数以固定源码中对应任务的帮助为准，例如 `uv run --frozen python scripts/export.py Mjlab-Velocity-Flat-MicroDuck-HD1910 --help`。导出时保留观测归一化，不能把“图能加载”当作运行合同正确。

先用同一个 **HD1910 任务**回放所选 checkpoint：

```bash
uv run --frozen play Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --checkpoint-file "$MICRODUCK_CHECKPOINT" --num-envs 1
```

这验证训练 checkpoint 的回放，不等于验证 ONNX。导出的文件还需做图检查、输入输出检查，并在适配了 HD1910 的 ONNX 回放器中核对相同观测下的输出与运动结果。

**本固定基线的通用 `scripts/infer_policy.py` 仍含 XL330 执行器路径与旧观测选项，不能直接用其默认值作为 HD1910 等效回放。** 匹配的 ONNX 回放器与模型部署工具应由维护人员随训练方案提供；没有时记录此项未完成，不把 checkpoint 回放或图检查冒充通过。

预览中的动作尺度、滤波、HOME、控制频率和执行器必须与待部署合同一致；文件扩展名相同不代表执行过程相同。`play` 参数参考锁定的 [mjlab 1.3.0 源码](https://github.com/mujocolab/mjlab/blob/v1.3.0/src/mjlab/scripts/play.py)。

## 7. 核对部署合同

本教程参考运行时的常见接口为 50 Hz、61 维观测、14 维动作，嘴轴独立管理。但具体模型始终以导出合同为准，不能只靠维度判断兼容。

| 要核对的项 | 为什么需要 |
| --- | --- |
| ONNX SHA256、输入输出名称与形状 | 确保验证和部署的是同一个文件 |
| 关节名称、动作顺序、方向与限位 | 避免数字合法却驱动错轴 |
| 观测顺序、单位、归一化、历史状态 | 避免输入含义错位 |
| HOME / 默认角度 | 决定动作基准和模型切换条件 |
| 控制频率、P/D、限力与电压处理 | 决定真机执行效果 |
| 动作尺度、EMA/低通、上一动作定义 | 改变闭环行为，不能随意为“更柔和”而修改 |
| 用途与停止/切换条件 | 区分行走、坐站、起身等策略 |

## 8. 生成 Studio 部署包，再回到实机验收

按配套导出/适配工具生成 `manifest.json`、`deployment-contract.json`，与 `policy.onnx` 和相关执行元数据放在同一包中。仅导出 ONNX 时，这一步尚未完成；需要模型提供方补充或由维护人员做部署适配，不能按猜测手填。

顺序：

```text
仿真回放 → 文件身份与合同核对 → robotd 无硬件模型预检
→ Studio 导入 → 卸力状态选用并读回
→ 重做必要标定 → 按第 07 章逐级实机测试
```

保留上一份已验证模型与配置以便恢复。别人报告“实机走得好”，只证明对方那一套硬件和运行环境的结果；导入成功、维度正确和本机步态稳定要分别记录。
