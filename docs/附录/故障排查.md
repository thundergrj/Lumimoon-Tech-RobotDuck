# 故障排查

[返回首页](../../README.md)

先记发生时间、正在做的操作、模型、供电和日志。一次只改变一个因素。没有新鲜状态时，不重复发送站立、行走命令。

## 1. 先判断卡在哪一层

| 检查 | 结果与含义 |
| --- | --- |
| 电脑能否访问路由器 | 失败先检查电脑网络；不要立刻重刷鸭子 |
| 当前 IP 是否属于鸭子 | 看路由器租约、主控 `hostname -I`；旧地址可能变化 |
| IP 能否回应、端口是否可达 | ping 只能辅助判断，不能单独证明系统或应用正常 |
| Studio 首页能否返回 | HTTP 正常只说明网页服务可访问，还要看实时连接 |
| Studio 是否收到新鲜 robotd 状态 | 主程序正常才继续检查总线、姿势、模型 |
| 15 颗舵机与 IMU 是否持续更新 | 单次扫描全到不能代替连续回读稳定 |

以下地址是示例，换成当前 IP，在电脑执行：

```bash
ping 192.168.1.123
curl --connect-timeout 3 --max-time 5 http://192.168.1.123:8000/
ssh -v -o ConnectTimeout=5 radxa@192.168.1.123
```

## 2. SSH 与网页都打不开

检查主控是否供电、是否反复重启、是否真的加入 Wi-Fi、IP 是否变化、电脑是否在隔离的访客网、代理是否接管局域网流量。灯常亮不能排除系统卡住或 Wi-Fi 离线。

若能接屏幕键盘，在瑞莎本机检查：

```bash
uptime
hostname -I
nmcli device status
systemctl status ssh.service ssh.socket microduck-studio.service --no-pager
sudo journalctl -b -n 100 --no-pager
```

主控所有已知地址都无法访问时，无法通过远程工具确认卸力、关机或回退是否完成；应使用本机终端/合适的调试接口恢复，不把网络超时当作关机成功。

## 3. Studio 能开，SSH 连不上

SSH 报错有不同含义：

| 现象 | 排查重点 |
| --- | --- |
| Connection refused | 地址、端口、ssh/ssh.socket 是否监听 |
| banner exchange 超时 | TCP 已连上但 SSH 欢迎信息没返回，检查服务状态、系统负载和日志 |
| Permission denied | 用户名、密钥/密码登录策略与 authorized_keys |
| 主机密钥变化警告 | 先核对是否重刷或连到别的设备，不盲删全部 known_hosts |

瑞莎本机检查配置与日志：

```bash
sudo sshd -t
sudo journalctl -u ssh.service -b -n 100 --no-pager
sudo ss -lntp
```

`sshd -t` 无报错后，再视实际情况 `sudo systemctl restart ssh.service`。若配置错误，先修配置。不要通过改成所有人通用密码来恢复访问。

## 4. 网页能开，但“鸭子没回话”

1. 确认使用 `http://实际IP:8000/`，查看实时连接标记，不看旧画面。
2. 检查主程序服务与本地 socket，查看启动日志。
3. 确认是否还在舵机页接管总线；如是，扶稳卸力后通过页面交还。
4. 查实际运行模式与启动阶段：标定模式正常存在，但一直 `configuring_bus` 或 `waiting_for_bus` 需要排查。
5. 核对协议版本、配套小助手、标定文件、串口和权限。界面提示含糊时导出诊断包，不直接把它当成网络问题。

```bash
systemctl status robotd.service --no-pager
systemctl cat robotd.service
sudo journalctl -u robotd.service -b -n 120 --no-pager
ls -l /run/robotd.sock
sudo fuser -v /dev/ttyS2
```

不要手动删除 `/run` 中的总线交接标记或另起一个 robotd 来强抢串口。

## 5. 扫不到或时好时坏

先断电核验 J13 转接线。参考 HAT 与 HD1910 的 1、3 脚定义相反，DATA/GND 要按电气名称对接。然后从单颗、短线、确认过的电源开始逐段加入。

检查：1 Mbps 是否统一、ID 是否重复、getty/启动控制台是否占口、端子是否退针、地是否可靠、供电动作时是否跌落、线束是否在关节运动时受拉。

有 IMU ID 200 的回应只证明该地址能答复，不证明芯片数据、协议解码、坐标方向和时间新鲜度正确。

## 6. 读不出当前姿势，不能站起来

暂停动作，核对：

- 主程序回读是否新鲜，15 颗是否齐全。
- 扭矩状态是否确认，是否存在卸力待确认、起身中或上次动作未完成。
- 重启后标定是否仍有效，运行模式是否正确。
- 现场是否确实卸力，有无某颗仍在保持。

无法确认时托住机体，使用正常卸力流程并等新回读；读不到某颗时不假装已全部卸力。不要强行改变姿势枚举或绕过按钮门槛。

## 7. 模型导入成功，仍不能确认运行配置

依次检查：真实连接 → 标定/运动模式 → 模型运行器是否启用 → 配套 API 能力 → 模型用途是否选用 → 运行端模型路径/身份是否读回一致。

部署包解析成功、无硬件预检成功、模型实际选用、策略执行和实物走路分别验收。不要把降低检查标准当成修复。

## 8. 地上不走，提起来会摆腿

先确认有非零速度输入且行走策略确实执行。记录承重与悬空时的目标位置、反馈、实际输出轴、电压、IMU 和接触条件。随后检查电机模式/参数、机械干涉、关节方向、重心、脚底和模型合同。

这个现象不能单独证明电源不足、IMU 错误或模型不兼容，悬空表现也不能作为行走通过的依据。按第 07 章逐级复测，不先加大 P 或动作幅度。

## 9. 启用摄像头后才开始失联

把新增服务作为优先排查对象，先恢复基本控制。确认卸力并保存日志后，在本机终端停用尚未验收的服务：

```bash
sudo systemctl disable --now --no-block mediad.service
sudo journalctl -u mediad.service -b -n 150 --no-pager
sudo journalctl -k -b -n 150 --no-pager
```

再检查 SSH、温度、内存、进程阻塞、供电和重启后稳定性。出现于摄像头启动之后是排查线索，还不能直接确定为过热或某个驱动问题。详见[摄像头附录](摄像头扩展与网络恢复.md)。

## 10. 提交给维护人员的信息

提交硬件版本、镜像/Studio/robotd/模型版本、发生时间、最后一步操作、错误原文、接线照片、动作与回读是否一致，以及 Studio 诊断包。不要只写“没反应”。保留原始文件，外发前核对其中的设备标识与网络信息。
